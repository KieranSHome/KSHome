## Introduction

One of the most useful parts of building a home lab is discovering what happens when something that normally works suddenly stops working.

This week, I investigated remote-access problems with my self-hosted Jellyfin media server. Requests through my custom domain began returning a **502 Bad Gateway** error, even though Jellyfin was available on the local network.

Rather than rebuilding the setup, I worked through the connection path and changed one variable at a time.

## Understanding the setup

My environment includes:

- **Jellyfin** for hosting and streaming media.
- **Windows 10** as the server operating system.
- **Caddy** as the reverse proxy handling HTTPS.
- **A custom domain** for remote access.
- **Proton VPN** on the same computer.

A working application does not necessarily mean the entire service is working. The application, network interface, reverse proxy, DNS and VPN can each affect the final connection.

## Working through the problem

I checked Jellyfin's health endpoint and compared access through the local network with access through the public domain. That helped separate application availability from the external connection path.

I also examined the Windows listener and Caddy's reverse-proxy configuration. During the investigation, the service was listening on the LAN address rather than loopback, which mattered because the proxy was configured to contact 127.0.0.1:8096.

After disabling Proton VPN, remote access started working again. That resolved the immediate issue, although it did not prove that every part of the VPN configuration was responsible. The investigation also highlighted the importance of ensuring that the proxy's upstream address matches the address on which the application is listening.

## What I learned

1. **Test from the inside out.** Check the application locally before investigating external access.
2. **Understand the request path.** DNS, the network interface, HTTPS, the reverse proxy and the application all play different roles.
3. **Treat a 502 as a clue, not a diagnosis.** It often means the proxy could not obtain a valid response from its upstream service.
4. **Change one variable at a time.** This makes it easier to identify which change actually fixes the problem.
5. **Protect working services.** Troubleshooting should avoid unnecessary changes to the media library and other working configuration.

## What comes next

I want to improve the service's resilience, document the recovery process and deepen my understanding of Windows networking and reverse proxies.

Self-hosting is a practical way to learn how infrastructure components work together. It has also reinforced that troubleshooting is not just about finding a command that works; it is about collecting evidence, testing assumptions and understanding the result.
